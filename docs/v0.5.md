# BRANCH v0.5 — Whole-Genome Lossless Haplotype Assembly

Status: design proposal, in development on `feat/binned-assembly-v0.5`.

Companion viewer release: VariantPaths v0.5 (Schlein-Lab, separate repo).
Output format synchronized; both released together.

## Why v0.5

`branch assemble` (v0.2/v0.4) builds a single-pass overlap graph that
preserves every read's evidence (lossless), but its memory profile is
linear in input bp. On a 188 GiB login node:

- HG002 chr14:IGH (37 Mbp) → 2.5 GiB peak, ok
- HG002 chr14 full (4.6 Gbp) → 113 GiB peak, OOMs at 120 GiB cap
- HG002 whole genome (~90 Gbp) → projected ~2 TiB

Per-chromosome slicing was a previous workaround attempt — but it uses
pre-existing reference alignment as a filter, which violates de-novo
semantics: paralogs that map elsewhere are dropped, unmapped reads are
dropped, translocations are invisible.

v0.5 keeps the lossless guarantee, scales to whole genome on a normal
node, and adds CNV-awareness as a first-class output.

## How BRANCH v0.5 differs from hifiasm / Verkko / Flye

| Property | hifiasm / Verkko / Flye | BRANCH v0.5 |
|---|---|---|
| Sub-30 % VAF branches | dropped (consensus collapse) | preserved as graph nodes with VAF + confidence tag |
| Mosaic / somatic SNVs | invisible | first-class output, 1-bp branches allowed |
| CNV calling | derived from graph coverage | independent vPCR amplicon-counter channel |
| Reference role | required for scaffolding | post-hoc annotation, not load-bearing |
| Reads dropped during assembly | silently | all dropped reads named with reason in disposition records |
| Output format | dual-haplotype FASTA + (optional) GFA | standard FASTA + BED + extended-GFA (samtools / bedtools / Bandage friendly) |

We do not compete with hifiasm on speed-of-best-haplotype-WGS. We
occupy a different category: lossless mosaicism-aware whole-genome
assembly with CNV quantification.

## Architecture: 6 phases

```
INPUT: whole-genome FASTQ.gz stream (or BAM, ~30 M reads, ~90 Gbp)
       no reference required for the core pipeline

──────────────────────────────────────────────────────────────
PHASE 0 — k-mer histogram + bimodality detection
──────────────────────────────────────────────────────────────
   purpose: discover informative SNP loci without a reference
   method:  bloom-filter pre-pass + exact counter for survivors
   output:  per-k-mer count, predecessor + successor k-mer distributions
            bimodal-count detection → het-SNP candidate list
   peak RAM ~30 GiB, wall-time ~45-60 min single-pass on 64 cores
   re-uses:  src/graph/kmer_sketch.hpp (extend with TechProfile)

──────────────────────────────────────────────────────────────
PHASE 1 — reference-free haplotype discovery + master-tiling
──────────────────────────────────────────────────────────────
   1.1  read → haplotype routing
        per read: vote over the N most-informative SNPs from Phase 0
        majority + chain-of-evidence transitive vote
        outputs: hap1_reads, hap2_reads, ambig_reads
   1.2  per-haplotype overlap (re-uses existing branch assemble backend)
        runs on ~½ × N reads per worker, ~30 GiB peak each, parallel
   1.3  master-tiling-path-finder
        graph traversal: longest sparse tiling with maximum overlap
        quality. Each genome-position belongs to exactly one master read.
        Boundary between master tiles = clean midpoint cutover (no
        synthetic consensus; every output base is a real read base).
   1.4  pile-up of all reads against master-tiling
        re-uses: src/graph/read_db.cpp (existing pile-up infrastructure)
   1.5  master curation
        per-position: if master-base agreement < min_base_agreement →
                      swap to majority. If alt-base count ≥ min_coverage_branch
                      → mark as branch candidate. Below threshold → discard
                      as Q-error.
        Q-weighted evidence: each read's vote is weighted by its local
        Q-score at that position (sigmoid around Q=12).
        outputs: hap1_master.fa, hap2_master.fa, alt_candidates.tsv
   wall-time ~3-4 h, both haps parallel

──────────────────────────────────────────────────────────────
PHASE 2 — transitive branch attachment
──────────────────────────────────────────────────────────────
   2a  classify all reads vs hap1+hap2 (k-mer jaccard, fast)
       direct-branch reads:   match → divergence → match  (classical bubble)
       residual reads:        no clear hap match
   2b  cluster residual + ambig reads against each other (sketch-based)
   2c  for each cluster: find member with partial overlap to a hap or to
       a direct-branch → that's the cluster's anchor
   2d  transitive: clusters without direct anchor anchor via another
       anchored cluster (multi-hop BFS, max-depth from TechProfile)
   what's left = "graph orphans" = potentially novel sequences
   re-uses: src/graph/graph_filter.cpp for containment-aware merging

──────────────────────────────────────────────────────────────
PHASE 3 — vPCR auto-primer design + CNV counting
──────────────────────────────────────────────────────────────
   sliding-window k-mer entropy over hap1.fa + hap2.fa + branches:
     low-entropy windows = conserved sequence = good primer candidates
     high-entropy gap between two low-entropy windows at PCR-able
     distance (~200-3000 bp ONT, ~200-1500 bp HiFi)
       → amplicon
   for each amplicon:
     scan all reads, count those carrying both primer-binders in correct
     distance + orientation
     CN_estimate = read_count / expected_single_copy_count
     Wilson-95 % CI on CN
   output: amplicon definitions + count-table

──────────────────────────────────────────────────────────────
PHASE 4 — reference annotation (DEFAULT ON, pangenome-first)
──────────────────────────────────────────────────────────────
   primary:  --ref-pangenome HPRC=hprc-v1.1-mc-grch38.gbz
             minigraph or GraphAligner → which haplotype-paths a branch
             matches; multiple paths = "known polymorphism"
   fallback: --ref-linear GRCh38=... CHM13=...
             minimap2 asm20 (existing branch project linear-layer)
   per branch: one of
     known_polymorphism      (matches HPRC paths)
     grch38_only_match       (linear yes, pangenome no)
     novel_to_pangenome      (no HPRC, no linear → genuine novelty)
     paralog_ambiguous       (multiple equally-good anchors)
   re-uses: src/project/linear_mapper.cpp + pangenome_mapper.cpp + somatic_delta.cpp
            (the entire existing branch project subcommand)

──────────────────────────────────────────────────────────────
PHASE 5 — orphan re-clustering
──────────────────────────────────────────────────────────────
   orphans (Phase 2 leftover reads with no hap or branch anchor):
     re-cluster against each other via sketch
     report each cluster: member count, consensus hint, attempted
     reference annotation (if any), best-partial-match score
   purpose: surface novel inserts, low-coverage assemblies, contamination,
            or unusual library artefacts — all distinguishable to the
            user via orphan_cluster_id + best-match-score.
```

## TechProfile — single source of all tech-specific thresholds

```cpp
struct TechProfile {
    // Phase 0
    size_t minimizer_k;            // hifi: 21   ont: 15
    size_t minimizer_w;            // hifi: 19   ont: 10
    size_t bucket_cap;             // hifi:  0   ont: 64
    int    expected_coverage;      // hifi: 30   ont: 35   (default; user-override)
    double bimodality_z;           // hifi:  4.0 ont:  2.5

    // Phase 1
    double min_base_agreement;     // hifi:  0.95 ont:  0.70
    int    min_coverage_branch;    // hifi:  2    ont:  3
    int    min_branch_length_bp;   // 1 (both — somatic-SNV detection)

    // Phase 2
    double sketch_jaccard_lo;      // hifi:  0.20 ont:  0.05
    int    max_transitive_depth;   // hifi:  3    ont:  5

    // Phase 3
    int    primer_min_window_bp;   // hifi: 18    ont: 25
    int    primer_max_window_bp;   // hifi: 25    ont: 40
    double primer_max_entropy;     // hifi:  0.5  ont:  0.8

    const char* name;              // "hifi" | "ont"
};

inline constexpr TechProfile kProfileHiFi = { 21, 19,  0, 30, 4.0,
                                              0.95, 2, 1,
                                              0.20, 3,
                                              18, 25, 0.5, "hifi" };
inline constexpr TechProfile kProfileONT  = { 15, 10, 64, 35, 2.5,
                                              0.70, 3, 1,
                                              0.05, 5,
                                              25, 40, 0.8, "ont"  };
```

Mixed HiFi+ONT (Verkko-style) is out-of-scope for v0.5 first cut.
Architecture leaves room: per-read tech-tag in ReadBatch is already
prepared via the BAM RG-line.

## Output: 3 standard files + auto-indices

```
HG002.fa.gz       FASTA: hap1 + hap2 + branches + orphans
HG002.fa.gz.fai   samtools index (auto)
HG002.fa.gz.gzi   bgzip index (auto)

HG002.bed.gz      BED: branches + CNV positions + ref-class annotations
HG002.bed.gz.tbi  tabix index (auto)

HG002.gfa.zst     extended GFA1.2 (zstd-compressed):
                    standard records (S, L, P, W) for the assembly graph
                    custom #-prefix metadata blocks for v0.5 extras
```

### `.gfa.zst` extension scheme — custom metadata via `#`-comments

GFA1.2 specifies `#` lines as comments. Standard readers (Bandage,
minigraph, vg) ignore them. We use a structured prefix for our
extras so a `grep -E "^#vpcr"` is enough to extract any one block:

```
##VPF v5.0
##assembler branch v0.5.0
##sample HG002
##read_tech ont
##haplotype_count 2
##phase_complete 0,1,2,3,4,5

# Master-tiling per haplotype (Phase 1)
#vph hap=hap1 length=145200000 master_tiles=12345
#vph hap=hap1 tile=0 start=0 len=22500 master=PAW70337-r12345 qmean=23
#vph hap=hap1 tile=1 start=22500 len=18900 master=PAW70337-r78911 qmean=24
...

# Curation log (Phase 1.5)
#cur hap=hap1 pos=42583125 from=A to=G n_support=47 reason=isolated_q_error

# vPCR amplicons + counts (Phase 3)
#vpcr amplicon=IGHG4_main fwd=AAGCT... rev=TGCCG... count=18 cn=4.2 ci=[3.8,4.6]

# Per-read disposition (Phase 1-5)
#disp read=PAW70337-r12345 phase=1 outcome=hap1 role=master tile=0
#disp read=PAW70337-r99001 phase=2 outcome=branch anchor=hap1:42M conf=0.92
#disp read=PAW70337-r99012 phase=2 outcome=orphan cluster=oc_0042
#disp read=PAW70337-r99013 phase=0 outcome=dropped reason=mean_q_below_8

# Orphan re-clusters (Phase 5)
#orphan cluster=oc_0042 size=34 ref=chr1:satellite-region best_score=0.30

# Run log (final block)
#log phase=0 wall_seconds=2400 peak_rss_gb=12.3 reads_processed=29845392
#log phase=1 wall_seconds=12500 peak_rss_gb=28.4
...

# Standard GFA records (S, L, P, W) below
S    hap1            ATCG...                  LN:i:145200000 RC:i:34521
S    hap2            ATCG...                  LN:i:145100000
S    branch_0001     ATCG...                  VA:f:0.05 CF:f:0.92 RC:Z:novel_to_pangenome
S    orphan_oc0042c1 ATCG...                  OC:i:42 SZ:i:34
L    hap1    +   branch_0001    +    1234M   AT:Z:hap1:42583125
P    hap1                hap1+
P    branch_path_001     hap1+,branch_0001+,hap1+
W    PAW70337-r12345     0   hap1    0       22500
```

Auxiliary tags on `S` records:
- `VA:f:` — VAF estimate
- `CF:f:` — confidence score (Q-weighted evidence)
- `RC:Z:` — ref class enum
- `OC:i:` — orphan cluster id
- `SZ:i:` — orphan cluster size
- `HP:i:` — haplotype index (0=hap1, 1=hap2, 2=both, 3=orphan)
- `MR:Z:` — master read id (for haplotype tile derivations)

### Why this output shape

| Tool | Reads what | Pipeline-friendly? |
|---|---|---|
| samtools | `HG002.fa.gz` (with auto .fai) | yes |
| minimap2 / bwa | `HG002.fa.gz` as reference | yes |
| bedtools | `HG002.bed.gz` (with .tbi) | yes |
| tabix | `HG002.bed.gz` for region queries | yes |
| IGV | `HG002.fa.gz` + `HG002.bed.gz` as track | yes |
| Bandage / gfaviz | `HG002.gfa.zst` (zstd-decompress on load) | yes |
| vg / minigraph | `HG002.gfa.zst` as pangenome input for next sample | yes |
| awk / grep / sed | full-text on uncompressed gfa | yes |
| VariantPaths | native reader for the full .gfa.zst | yes (added in VP v0.5) |

No silent breakage of standard pipelines. No `branch extract` required
for any common operation.

### Optional `--bundle` mode

For users who need a single-file artefact (email, cloud upload):
`branch wg --reads X --out-prefix HG002 --bundle` writes additionally
`HG002.tar.zst` containing the 3 files + indices. Default off.

## CLI surface added in v0.5

```
branch wg              the full whole-genome pipeline
branch extract         pull standard-format views from the .gfa.zst
                       (used internally for VariantPaths users who want
                       FASTA / BED / VCF on demand without re-running)
```

Existing subcommands unchanged: `assemble`, `analyze`, `project`, `version`.

### `branch wg`

```
branch wg \
    --reads HG002.fastq.gz                      input reads
    --read-tech {hifi,ont}                       tech profile (default hifi)
    --ref-pangenome NAME=path.gbz                pangenome ref(s), repeatable, default-on
    --ref-linear NAME=path.fa                    linear ref(s), repeatable
    --threads 64
    --out-prefix HG002                           emits HG002.{fa.gz,bed.gz,gfa.zst}
    [--phase 0,1,2,3,4,5]                        run only specified phases
    [--resume-from <phase>]                      pick up after a crash
    [--bundle]                                   also write HG002.tar.zst
    [--no-ref-annotation]                        skip Phase 4 (non-human samples)
    [--no-vpcr]                                  skip Phase 3
    [--keep-intermediate]                        keep .tmp/<phase>/ work directory
    [--max-memory 100G]                          per-process memory cap
```

Per-phase tunables (override TechProfile defaults):
```
    [--min-base-agreement 0.7]
    [--min-coverage-branch 3]
    [--min-branch-length-bp 1]
    [--bimodality-z 2.5]
    ...
```

### `branch extract`

```
branch extract HG002.gfa.zst <view> [args...]

Views:
  hap1                hap1 sequence as FASTA on stdout
  hap2                hap2 sequence as FASTA on stdout
  branches            branch sequences only (FASTA)
  orphans             orphan cluster consensus sequences (FASTA)
  vpcr                vPCR amplicons + counts (TSV)
  disposition         per-read disposition log (TSV)
  curation            master curation log (TSV)
  log                 run log (JSON)
  graph               GFA without #-comments (Bandage-only)
```

Each view is a streaming filter over the .gfa.zst — no temp files, no
duplicate state. `branch extract HG002.gfa.zst hap1 > hap1.fa` is
sufficient for any downstream FASTA pipeline.

## Validation plan

Empirical calibration of TechProfile defaults via:

1. **HG002 GIAB v4.2.1 high-confidence regions** as truth set
   - Branch detection sensitivity: how many known SNV/INDEL/SV are recovered?
   - FDR estimate: how many branches outside truth-confident regions vs. inside? 
   - Note: n=3 reads cannot be falsified to truth. We report likelihood
     scores per branch (Q-weighted evidence + read-quality summary), not
     binary pass/fail. User decides thresholds.

2. **Paralog locus stress-test**
   - IGH (chr14:105.4-106.5M)
   - KIR (chr19:54.7-55.4M)
   - MHC (chr6:28-34M)
   - Verify branches recover known paralog-allele diversity better than
     hifiasm/Verkko collapse.

3. **Mosaicism-aware dataset**
   - HG002 LCL with known clonal subpopulations (existing in our IGH paper data)
   - Recover sub-30 % VAF events that hifiasm consensus drops.

4. **Memory + time profiles per phase**
   - Whole-genome HG002 ONT (90 Gbp): expected total ≤ 8 h, peak RAM ≤ 100 GiB
   - Whole-genome HG002 HiFi (90 Gbp): expected total ≤ 6 h, peak RAM ≤ 80 GiB

5. **Lossless guarantee audit**
   - Sum of (in-output reads) + (disposition-listed dropped reads)
     must equal input read count, exactly.
   - Per-phase counter dumped in `#log` block.

## Open questions to calibrate empirically

These defaults are educated guesses; HG002 calibration runs will refine:

- `bimodality_z`: 2.5 (ONT) vs 4.0 (HiFi) — too low → false het-SNP
  candidates; too high → miss real SNPs in low-coverage regions.
- `min_coverage_branch`: 3 (ONT) vs 2 (HiFi) — Q-weighted, not raw,
  so the effective threshold is higher than nominal.
- `sketch_jaccard_lo` for Phase 2 clustering: 0.05 vs 0.20 — controls
  how "loose" residual reads cluster.
- `max_transitive_depth` for Phase 2: 3 (HiFi) vs 5 (ONT). Deeper =
  more noise tolerance, but also more anchor-uncertainty.

The TechProfile struct exposes all of these; CLI flags for each
allow per-run override. We document defaults + observed behaviour
in a release-notes section after the first calibration runs.

## Out of scope for v0.5

- Hybrid HiFi+ONT (Verkko-style mixed-tech)
- Polyploid / trio binning
- GPU bin-assembly path (CPU only first; GPU port if memory profile justifies)
- Iterative read-correction (Canu/hifiasm-style)
- Inline VCF output (use `branch extract` for downstream VCF pipelines)

These are flagged as v0.6 candidates, not v0.5 work items.

## Modular usage — replacing hifiasm/Flye/Verkko piecewise

Default `branch wg` runs all phases. But every phase is also a
standalone subcommand with its own input/output contract, so users
who already have an assembly from hifiasm/Flye/Verkko can drop in
**only the parts they need** from BRANCH.

### Per-phase subcommands

```
branch wg-kmer-hist     Phase 0:  reads → k-mer-hist + SNP candidates
branch wg-haplotype     Phase 1:  reads + SNPs → hap1.fa, hap2.fa, master tiles, curation
branch wg-attach        Phase 2:  reads + haps → branches + orphans
branch wg-vpcr          Phase 3:  haps + branches → vPCR amplicons + counts
branch wg-annotate      Phase 4:  branches + refs → ref_class annotations
branch wg-orphans       Phase 5:  orphans → re-clusters
branch wg               convenience: runs 0 → 1 → 2 → 3 → 4 → 5 in order
```

Each subcommand reads/writes the same `.gfa.zst` file in-place,
appending its phase's records and `#log` block. State carries over
seamlessly between manual phase invocations and full-pipeline runs.

### Common usage modes

**As a hifiasm replacement (phased haplotype assembly only):**
```
branch wg-kmer-hist --reads X.fastq.gz --read-tech ont --out X.gfa.zst
branch wg-haplotype --reads X.fastq.gz --in X.gfa.zst
# X.fa.gz now contains hap1 + hap2 — drop in to your existing pipeline
```
Equivalent shortcut:
```
branch wg --reads X.fastq.gz --phase 0,1 --out-prefix X
```

**As a CNV-quantifier on an existing hifiasm/Flye/Verkko assembly:**
```
# you already have an assembly.fa from hifiasm
branch wg-import-fasta --in assembly.fa --out X.gfa.zst    # treats as fixed haps
branch wg-vpcr --reads X.fastq.gz --in X.gfa.zst
# X.bed.gz now lists vPCR amplicons + CN estimates
```

**As a branch-detector on an existing assembly + reads:**
```
branch wg-import-fasta --in assembly.fa --out X.gfa.zst
branch wg-attach --reads X.fastq.gz --in X.gfa.zst
# branches + orphans appended to X.gfa.zst
```

**As a ref-annotator on existing branches:**
```
# you already have your_branches.fa from elsewhere
branch wg-import-branches --in your_branches.fa --out X.gfa.zst
branch wg-annotate --in X.gfa.zst --ref-pangenome HPRC=path.gbz
# ref_class added to every branch S-record in X.gfa.zst
```

### Why modular > monolithic

- **Trust gradient**: a user who trusts hifiasm's haplotype assembly but not its CNV calls can bring our Phase 3 only.
- **Iteration speed**: re-running Phase 4 with a new pangenome ref is seconds, not the full WG pipeline.
- **Adoption path**: tool can be brought in piecewise without overthrowing an established workflow.
- **Testing per phase**: integration tests don't need a full WG run for every change.

The `.gfa.zst` accumulates state across invocations. The `##phase_complete` header line is updated each time, and `branch wg-status X.gfa.zst` prints what has been done so far.

### Subcommands also exposed as `branch ...` aliases

For convenience, the most common single-phase tasks get top-level aliases:

```
branch haplotype  =  branch wg-haplotype
branch vpcr       =  branch wg-vpcr
branch annotate   =  branch wg-annotate   (delegates to existing branch project under the hood)
```

So a hifiasm-replacement workflow reads cleanly:
```
branch haplotype --reads X.fastq.gz --read-tech ont --out X
```
